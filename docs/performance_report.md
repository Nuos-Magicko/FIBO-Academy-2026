# Performance measurement report: preliminary characterization, unit #1

**Date:** 2026-10-15 · **Board:** gmt-8e6dd8 (MAC 8c:bf:ea:8e:6d:d8), OV3660 · **Firmware:** `2959028` (clean build) · **Audience:** GMT and mentors

> **This is not the reference baseline.** It was measured without a heatsink, with the camera lying sideways on an office desk (people occasionally in view), and with the room temperature not measured. It shows how the unmodified system behaves and that the measurement chain works end to end. The Gate 4 baseline (heatsink fitted, reference scene, room temperature recorded, tag `baseline-v1`) must replace these numbers before they're used for comparison.
>
> **Don't hand this report to students before they have measured the system themselves.** It would answer questions they're meant to investigate (`mentor_notes.md`).

All numbers below were measured on hardware unless stated otherwise. Timing boundaries are defined in `experiments.md` §1. Nothing was tuned.

## 4. Limits of these measurements
- **No heatsink, uncontrolled scene, room temperature not measured.** These are the main reasons this is not the baseline.
- **One board.** Unit-to-unit variation is unknown.
- **Mode order is fixed,** so mode effects and thermal or time drift are confounded. Each mode ran for only 75 s per repeat.
- **The Wi-Fi conditions were not controlled:** shared office network, people moving, other traffic. Variation in t_send and drops is real, but it's specific to this place and time.
- **Few detections in view.** Postprocess and grid costs scale with detections, so their live values here are lower bounds for a busy scene.
- **METRICS share the socket with frames.** During send stalls, METRICS windows are delayed or merged (156 windows recorded in 180 s of `full_stream`). Window counts per trial therefore vary.
- **What "capture → display" covers:** it starts when `esp_camera_fb_get()` returns, not at exposure, and it is only valid to within the stated ± bound.

## 5. Harness issues found during measurement, and fixed
1. **Baseline script (then `scripts/collect_baseline.py`, now `pc/main.py baseline`): trial boundary.** The hand-off from warm-up to measurement could split a JPEG_FRAME from its DETECTIONS, creating a false "missing pair" (§3.3 †). It now hands over only at a frame boundary. A smoke test of 2 repeats × 2 modes gave 0 missing pairs.
2. **Baseline script: final restore.** The "back to `full_stream`" command was sent and the socket closed at once. The unread HELLO caused a TCP reset and the device discarded the command, leaving the board in the last trial's mode. It now waits for the confirming HELLO. This didn't affect the data above: each trial confirms its own mode, and the soak rebooted the board.
